UIRefiner 是怎么工作的

用一句话说清：AI 说"要什么"，程序做"怎么改"。

LLM 不直接改代码——它写一张"点菜单"，由执行器照单修改界面

①先讲一个餐厅的比喻

你在一家餐厅说"我要一份微辣、少盐的番茄牛腩"，会发生什么？

🗣️

你（用户）

用大白话说需求：
"把提交按钮挪到上面"

→
📝

服务员（LLM）

把大白话写成一张规范的点菜单：菜名只能从菜单上选，写法有固定格式

→
👨‍🍳

后厨（执行器）

核对菜单是否合法，照单做菜。
菜单上没有的菜，后厨做不出来

LLM 就是那位服务员：它擅长"听懂人话"，但我们不允许它进后厨。这是整个系统安全性的根基。

②系统由三块积木搭成

对应到产品里，就是三个各司其职的部件。

说明书

界面说明书 （控件树）

软件界面不是画死的图片，而是按一份"说明书"实时画出来的：这个页面有哪些字段、哪些按钮、谁在上谁在下。

  • 改了说明书 = 改了界面
  • Agent 靠读它来"看见"界面
点菜单

布局意图清单 （DSL）

LLM 的输出。格式固定、动作封闭，只有九种："移动 / 隐藏 / 显示 / 折叠 / 改名 / 分组 / 调列 / 调属性"等。

  • 像乐谱：LLM 写谱，不同乐器都能演奏
  • 可预览、可撤销、可存档
后厨

执行器 （引擎）

真正动手改说明书的那只手。它不认识 LLM，只认识点菜单——照单核对、照单修改，一次只做菜单上允许的事。

  • 预览和正式应用用的是同一段代码
  • 两条产品路线只是"手"不同

③一次修改的完整旅程

就用你说的那个例子："把提交审核按钮挪到表单上方"。整个过程约 2 秒。

你说出一句话 用户

在右侧 AI 面板输入，或点一条高频指令。

Agent 翻开"界面说明书" 系统

把当前页面的控件清单（每个控件的名字、类型、位置）和你的话一起交给 LLM——它必须照着真实存在的控件说话，不许编造。

LLM 写出"点菜单" LLM

它没有改任何代码，只是产出一份结构化清单：

{
  "动作": "移动",
  "谁":   「提交审核」按钮,
  "到哪": 「工单表单」之前
}
// 实际是 JSON：{"action":"move","target":"button-submit","before":"form-ticket"}

三道安检 系统

① 格式对不对（是合法 JSON 吗）→ ② 动作在九种词汇表里吗 → ③ 提到的控件真实存在吗。任何一道不过关，就把错误原因发回给 LLM 重写（最多两次），再不行就请用户从候选里点选——绝不会"硬着头皮乱改"。

预览：先看后买 系统

改之前

提交审核（在底部）
⇄

预览（改之后）

提交审核（在上方）

不点"应用"，什么都不会发生。

执行器照单修改说明书 系统

确认后，执行器在说明书上把按钮"剪下来、贴上去"，界面立即重新绘制——按钮出现在表单上方，而且点它还是触发原来的业务动作，因为只挪了位置，没动任何逻辑。

改动存档为"差量" 系统

原始应用一个字节都没被改。这次修改以一条"差量记录"存档（谁在什么时候、动了什么），可单独撤销、按角色保存——这是"升级不丢"的伏笔。

④为什么它"改不坏"？

安全不是承诺出来的，是设计出来的——三道保证层层兜底。

🚫

结构上不可能越界

LLM 只能"点菜"，而菜单上没有"改数据""改金额""改审批流"这些菜。想让它改业务逻辑？它在格式层面就无法表达。

🔎

错误在最低成本处暴露

就算 LLM 理解偏了，也只会在安检或预览环节被人看见并否决；真实应用前还有人工确认这道闸门。

↩️

一切皆可撤销

原始应用零修改，所有定制都是"差量"。每条差量可单独撤销；软件升级后差量照常生效（路线 B）。

⑤一套大脑，两只不同的手

Demo 演示的两条接入路线，共享同一个"理解层"，只是落地方式不同。

🧠 理解层：LLM + 布局意图清单听懂人话 → 写出点菜单 → 三道安检（两个应用完全相同）

路线 A · 自研 Web 应用

🤲 手：SDK 执行器（装在应用里）
  • 适合有源码的自研系统
  • 改动即时热更新，无需重启
  • 可看每笔改动的 SDK diff，一键导出变更包交开发商合入标准版

路线 B · 存量 ERP（SAP 式）

🤲 手：厂商适配层（差量叠加）
  • 适合没有源码、但厂商留了"适配接口"的企业软件
  • 差量按角色保存：销售岗和财务岗看到两套界面
  • 升级安全：厂商升级应用后，所有定制自动重放依然生效

⑥四个最常被问到的问题

Q1：LLM 是直接改代码吗？

不是。它从头到尾没碰过一行代码，甚至不知道代码放在哪。它只输出一份"点菜单"，改代码（准确说：改界面说明书）的是执行器。

Q2：它会把业务逻辑改坏吗？

结构上不可能。按钮挪了位置，点击后触发的还是原来那个业务动作。DSL 词汇表里根本不存在"改数据""改计算"这类动作，LLM 想改也没有语法可写。

Q3：AI 理解错了怎么办？

三重保险：格式/词汇/控件存在性三道安检不过就自动重写；过了安检也要预览确认才生效；生效后每条改动都能单独撤销。理解错误的代价被封顶在"预览时被你看见"。

Q4：软件升级后，我的定制还在吗？

路线 B 的杀手锏：在。因为定制是"差量"，和原始应用分离存储。厂商升级（甚至新增字段）后，差量自动重新叠加——Demo 里有一键模拟升级可以现场验证。
